## E. Alterações de configuração

Uma só, e ela é obrigatória:

```toml
# api/wrangler.toml, bloco [vars] de PRODUÇÃO
ORIGENS_PERMITIDAS = "https://gustavodemelomartins-hub.github.io,https://<projeto>.pages.dev"
```

**Por que:** o Worker de produção hoje aceita chamadas de um endereço só, o do
painel clássico no GitHub Pages. A V2 vai para um projeto Pages novo, e sem
esta linha o navegador recusa toda requisição — a tela abre e nenhum dado
chega. O painel clássico continua na lista: ele não sai do ar.

`<projeto>` é o nome do projeto Pages, a ser criado. **Este é o único valor
deste documento que ainda depende de uma escolha.** Sugestão: `marquesa`.

> `wrangler deploy` trata o `wrangler.toml` como fonte da verdade e APAGA
> variável de texto criada pelo painel que não esteja declarada ali. Por isso
> a mudança é no arquivo, não no painel da Cloudflare. Segredos não são
> afetados.

## H. A ordem exata do deploy

A ordem não é preferência. Cada passo depende do anterior:

```
1. backup          o D1 não tem desfazer; o bookmark é o rollback
2. migrations      o Worker novo lê colunas que ainda não existem
3. Worker          o código que usa as colunas novas
4. frontend        a tela que chama o Worker novo
5. CORS            já vai junto no passo 3 (é o wrangler.toml)
```

Inverter 2 e 3 põe no ar um Worker que consulta coluna inexistente. Inverter
3 e 4 põe no ar uma tela que chama rota que ainda não existe.

## I. Backup

**Obrigatório**, antes de qualquer migration.

```bash
# 1. o bookmark do Time Travel — é ele que desfaz uma migration
npx wrangler d1 time-travel info DB
#    ANOTAR o bookmark devolvido. Sem ele o rollback é manual.

# 2. o export completo, como segunda rede
cd api && npx wrangler d1 export DB --remote --output ../../marquesa-prod-2026-09-25.sql
```

> O export tem CPF, telefone e histórico de compra com nome. Ele fica
> **fora do repositório** (o caminho acima sai da pasta de propósito) e é
> apagado depois que a release fecha. `backups/` e `*.sql` de dump estão no
> `.gitignore`, mas o hábito é não depender disso.

## J. Rollback

| se falhar em | como voltar |
|---|---|
| migration | `npx wrangler d1 time-travel restore DB --bookmark <o anotado>` |
| Worker | `cd api && npx wrangler rollback` (volta à versão anterior) |
| frontend | painel do Pages → deployment anterior → "Rollback to this deployment" |
| tudo | restaurar o bookmark **e** `wrangler rollback`, nesta ordem |

O Worker de produção está hoje na versão `3e0f9da2-9ee1-4d17-b360-c17b613d15ca`
(publicada em 09/09/2026). **Anotar esta id antes de publicar** — é para ela
que `rollback` volta.

O frontend não tem "anterior" ainda: o projeto Pages será criado amanhã. O
rollback do frontend, no primeiro dia, é **apagar o projeto** — o painel
clássico continua no ar em `gustavodemelomartins-hub.github.io` o tempo todo,
intocado, e a operação não fica sem sistema em nenhum momento.

## O roteiro, passo a passo

### PRÉ-PROD

```bash
# o repositório
git fetch --all --prune
git log --oneline origin/develop -1          # confirmar o HEAD candidato
git status --short                            # tem de estar limpo

# os testes
cd frontend && npm ci && npm test && npm run build && cd ..
node src/migracao-variantes-test.mjs          # schema.sql ≡ migrations

# o estado REAL de produção, antes de tocar em nada
cd api
npx wrangler deployments list                 # ANOTAR a versão atual
npx wrangler d1 execute DB --remote --command \
  "SELECT COUNT(*) FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%' AND name NOT LIKE '_cf%'"
npx wrangler d1 execute DB --remote --command \
  "SELECT (SELECT COUNT(*) FROM produtos) produtos, (SELECT SUM(qtd) FROM produtos) saldo, (SELECT SUM(qtd) FROM movimentos) razao, (SELECT COUNT(*) FROM clientes) clientes, (SELECT COUNT(*) FROM vendas) vendas, (SELECT COUNT(*) FROM garantias) garantias"
#   ANOTAR os seis números. Eles são a prova de depois.
#   `saldo` e `razao` TÊM de ser iguais antes de começar.

# o backup
npx wrangler d1 time-travel info DB           # ANOTAR o bookmark
npx wrangler d1 export DB --remote --output ../../marquesa-prod-2026-09-25.sql
```

**Gate:** não seguir se `saldo != razao`, se algum teste falhar, ou se o
bookmark não foi anotado.

### DEPLOY

```bash
# 1. as dez migrations, UMA A UMA, na ordem do item C
cd api
npx wrangler d1 execute DB --remote --file migracao-catalogo-4-5.sql
#   … e depois de CADA uma, as seis contagens de novo.
#   Se qualquer uma se mover, PARE e restaure o bookmark.

# 2. o Worker — o wrangler.toml já leva o CORS novo
#    (confirmar que ORIGENS_PERMITIDAS tem os DOIS endereços antes)
npx wrangler deploy

# 3. o frontend
#    Actions → "Deploy PRODUÇÃO (Cloudflare Pages)" → Run workflow
#    confirmacao: PUBLICAR EM PRODUCAO
#    projeto:     <o nome escolhido>
```

O workflow de produção **não tem gatilho por push**: nenhum commit, merge ou
rebase o dispara. Ele só roda por "Run workflow" com a palavra digitada, e
falha no primeiro passo se ela não bater.

### PÓS-DEPLOY

Os quatro do item K, na ordem. Depois, à mão: Estoque · Inventário · Cadastro
de produto · Vendas · Financeiro · Revendedoras. E os logs:

```bash
cd api && npx wrangler tail          # deixar rodando durante o smoke manual
```

### ROLLBACK

Qualquer gate que falhar:

```bash
cd api
npx wrangler d1 time-travel restore DB --bookmark <o anotado no pré-prod>
npx wrangler rollback                                  # volta o Worker
# frontend: painel do Pages → deployment anterior, ou apagar o projeto
```

E as seis contagens de novo, para provar que a volta voltou.
